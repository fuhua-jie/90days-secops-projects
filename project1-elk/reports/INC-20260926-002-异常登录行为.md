## 一、事故概览

09-27 的凌晨到上午，出现了三个外网来源对soc进行了SSH攻击。02:10-02:19期间一个来源（**198.51.100.99**）用每40秒一次的慢节奏尝试15次数据库账号，全部失败——现有规则（5分钟失败>100）对它完全失明，它的最大5分钟窗口只有8次。03:17，第二个来源（**203.0.113.150**）用真实运维账号hua一次登录成功，没有登录失败的记录——更像是凭据泄露，不是爆破。11:42，第三个来源（**203.0.113.88**）24秒内尝试150次（root/admin）登录，全部失败，密度937.5条/分。

## 三、来源维度

**本节的统计口径为登录尝试次数** = `login_failed` + `login_success` = **173 次**。 **不按日志条数**，因为**一次失败的登录尝试会产生最多 3 行日志**（`Invalid user` + `Failed password` + `Disconnected`）；按日志行数统计会让"失败更多的人"被重复放大，与真实尝试次数不成比例。

## 五、行为维度与定性

| **ssh_event**     | **条数**  | **归属**                                                                                 |
| ----------------- | ------- | -------------------------------------------------------------------------------------- |
| **login_failed**  | **165** | **全部外网**                                                                               |
| **invalid_user**  | **90**  | **全部外网**                                                                               |
| **disconnect**    | **165** | **全部外网 【✅ 实测：165/165 携带 `ssh_ip`，2026-10-03 修补管道后】**                                   |
| **pam_unix**      | **16**  | **内网 14 + 外网 2【推断：无 `ssh_ip`，16 条 `ssh_name` 全为 `hua`，为 8 次成功登录的 session open/close】** |
| **login_success** | **8**   | **内网7+外网1**⭐                                                                           |
| **service_event** | **2**   | **本机**                                                                                 |
| 合计                | **446** |                                                                                        |

**「归属」列凡标【推断】者，均因该事件类型不携带 `ssh_ip`，结论由同 IP 的相邻事件关联得出。**

**关键比 = login_failed : login_success = 165 : 8 ≈ 20.6 : 1 —— 每 20.6 次失败才换来 1 次成功，说明绝大多数攻击被挡在门外；但唯一成功那次不需要任何失败铺垫。**

`203.0.113.150`**成功那次没有任何前置失败**，因此更像凭据泄露而非爆破。

**「行为定性与 MITRE 映射」：**

| **行为**               | **MITRE**                       | **战术**                       |
| -------------------- | ------------------------------- | ---------------------------- |
| **大量失败尝试**           | **T1110 Brute Force**           | **TA0006 Credential Access** |
| **Invalid user大量出现** | **可关联 T1087 Account Discovery** | **TA0007 Discovery**         |
| **有效凭据登录成功**         | **⭐** **T1078 Valid Accounts**  | **TA0001 Initial Access**    |

三条行为中**最高危的是 T1078（Valid Accounts）**：前两条只是【还在试】，而这一条是**已经进去了** —— 如果有效凭据在外网可用，攻击者不需要任何漏洞就能拿到合法会话，后续所有操作在日志里都是【正常登录】。

## 六、检测能力评估与改进建议

### 6.1 现有规则的实测盲区

本次场景假设的现有检测规则为：**5 分钟内 `login_failed` > 100 即告警**。

用实际数据回放这条规则（见「阈值规则盲区」面板）：`login_failed` 的 5 分钟对齐桶只有三格有数据 —— `02:10` = **8**、`02:15` = **7**、`11:40` = **150**。**只有 `11:40` 那一格会触发告警**。

这意味着规则漏掉了两个方向的攻击：

**其一，低速攻击。** `198.51.100.99`，02:10–02:19 每 40 秒尝试一次，全程 15 次失败，任何 5 分钟窗口内最多 8 次，**距阈值 100 差 12.5 倍**。攻击者不需要任何技术，只要把节奏放慢，就能完全绕过这条规则。

**其二，成功登录。** `203.0.113.150`，03:17 只有 1 条 `login_success`、**零条 `login_failed`**。这条规则统计的字段是 `login_failed`，因此**在原理上就不可能被它发现**——而这恰恰是本次唯一得手的行为。

结论：**现有规则的盲区不是"阈值调得不好"，而是它假设了"攻击一定表现为大量失败"。** 当攻击表现为"少量、慢速、且最终成功"时，这条规则的检出率为 **0**。

### 6.2 短期建议

根据现有的实测盲区我建议可以进行以下的改进：

1、把"全局总量"改成"按来源IP分组"，具体改法：`login_failed`，**`group by ssh_ip`**，窗口 **10 分钟**，阈值 **> 5**；为什么这么改不会误报，我以一个现有的例子来举例：`198.51.100.99` = **15 次 / 单一 IP** → 命中； `203.0.113.88`= **150** → 命中；内网基线 `192.168.103.1` = **0 次失败** → **零误报**；按 IP + 10 分钟 + 阈值 > 5 会带来新代价：正常用户连错 6 次密码将触发告警。这个代价可以接受（运营成本 = 看一眼工单），而漏报的代价是主机失陷。

2、**新增"外网 + 成功登录"高优告警**，具体改法：`ssh_event: "login_success" AND NOT ssh_ip.keyweord: 192.168.103.*`，**阈值 = 1**；改成阈值1是因为**成功登录不是一个"数量问题"，它是一个"状态变更"** —— 内网运维登录本来就该成功；外网成功只可能是事故。对状态变更设数量阈值是没有意义的。

3、`invalid_user` 出现即告警，具体改法：`ssh_event: "invalid_user"`，按 `ssh_ip` 分组， **阈值 = 1**；因为内网正常登录**不会**产生 `invalid_user`。

### 6.3 长期建议

更长期的建议就需要改进管道和思路了。

1、**检测从"数事件"升级为"看状态 + 看关系"**；
1. 状态类事件（成功登录、权限变更）单独建规则 
2. 引入同凭据在异常时间/异常来源使用的关联判断（UEBA 思路）；Day 48（280 次全失败）和 Day 49（1 次成功）**连续两天暴露同一个设计缺陷**：只看"某类事件出现多少次"。

2、**补齐日志管道，让每条事件都带来源 IP**（**2026-10-03 已落地**）：给 `disconnect` 分支加 grok
`"Disconnected from (?:invalid user |authenticating user )?%{USERNAME:ssh_name} %{IP:ssh_ip}"` → **165 条全部携带 `ssh_ip`**，字段覆盖率 263/446 → **428/446**；同时清理调试字段`log_timestamp` / `ssh_message`。剩余 **18 条（`pam_unix` 16 + `service_event` 2）在日志原文里本来就没有 IP，无法修复** —— 这划出了检测能力的**天花板**：**下限由管道决定，上限由日志源决定**；要覆盖这部分，只能引入别的日志源（`wtmp` / `auditd` / 应用层日志）。

3、给 `ssh_ip` 建 index template，映射成 `"type": "ip"` → CIDR、网段查询、Kibana Maps 全部可用。

4、沉淀内网基线白名单（网段 / 资产 / 运维账号）网段匹配统一写 `ssh_ip.keyword: 192.168.103.*`（**实测两种 mapping 下都命中 7**）；映射为 `ip` 之后**额外解锁** CIDR 写法 `ssh_ip: 192.168.103.0\/24`（命中 7；注意 Lucene 语法里 `/` 表示正则起始，**必须转义**，不转义会报 400）；本次能一眼看出 **`203.0.113.150`** 可疑，**正是因为"内网基线"这个概念存在**。没有基线，"外网来源"就不是一个可用判据。

## 七、待确认事项

1、`203.0.113.150`既然成功登录了那么他在这台机器上都做了什么？
验证方法：
① 取证窗口就是 **03:17–03:24 这 7 分钟**；
② `last -a` / `/var/log/wtmp` 看会话记录 ；
③ 检查 `~/.bash_history` 及其 **mtime** ；
④ 检查 `~/.ssh/authorized_keys` 是否被追加（持久化）。

2、`198.51.100.99`的低速爆破，真的放弃了吗？
验证方法：按 ssh_ip 做 terms 聚合，看 198.51.100.99 在当前索引之外是否还有记录；若有，改用 1 小时窗口 + 阈值 ≥3（低速攻击靠"持续多久"而非"多快"识别）。

3、`203.0.113.150` 的凭据从哪来？
验证方法：若该 IP 也出现在 Web 日志（nginx/access）中，则说明它先通过 Web 侧手段拿到凭据；若只出现在 auth.log，则更可能是密码复用或弱口令。
