# 一、踩坑笔记的写法（方法）

## 一个坑 = **六格 + 一个标签**

```markdown
### 坑 N：<一句话说清现象，不要抽象>

【现象】      我当时看到了什么？（带具体数字 / 报错原文 / 截图）
【我原来怎么想】我的错误假设是什么？
【实际是什么】  真相
【怎么找到的】  ★ 关键的那一步 —— 从现象到真相的推理链
【正确的做法】  以后怎么写 / 怎么敲（要能照着执行）
【一句话教训】  能背下来的一句
```

> 🎯 **六格里最容易被漏掉、也最值钱的是【怎么找到的】。**
>
> 因为**下次现象可能长得不一样，但"怎么找"的方法可以迁移**。
> 只写结论的笔记，三个月后你只知道"我踩过这个坑"，**还是不会查**。

## 按「静默 / 响亮」给坑分类

| 类别 | 特征 | 笔记重点 |
|---|---|---|
| 🔴 **静默坑** | **不报错、不警告，结果就是错的** | **必须写清楚"怎么检测出来"** |
| 🟡 **响亮坑** | 直接报错 / 服务不启动 | 写清"报错长什么样 → 怎么修"即可 |
| 🔵 **规范** | 环境、习惯、流程 | 归到「工作规范」，**不是坑** |

> **静默坑是真正吃时间的那些。** 响亮坑三分钟能修好，静默坑能耗你一晚上。

## 检验标准（写完自己过一遍）

```
□ 现象有具体数字 / 报错原文吗？（别人能复现吗）
□【怎么找到的】写了吗？—— 最容易被漏掉的一格
□【正确的做法】是一条可以照着敲的命令吗？
□【一句话教训】能背下来吗？
□ 三个月后重看，能不靠回忆直接排查吗？

只要有一个「否」→ 这条笔记还不算能用。
```

# 三、范例（两篇写全的）

## 坑 6：配置改对了，行为却没变 —— 因为有第二个配置文件在跑

**【现象】**

新灌进去的 446 条 SSH 日志，**全部**带上了 `_grokparsefailure` 标签。
但同一批数据的 `ssh_message` / `ssh_name` / `ssh_ip` / `@timestamp` **又全部正确**。

```
tags        : ["ssh", "_grokparsefailure"]      ← 说解析失败
ssh_message : "Failed password for invalid user oracle from ..."   ← 但明明解析成功了
ssh_event   : "login_failed"
@timestamp  : "2026-09-27T02:10:00.382Z"
```

**「解析成功」和「解析失败」同时成立** —— 逻辑上矛盾。

**【我原来怎么想】**

以为是 web 的 `%{COMBINEDAPACHELOG}` grok 没有被 `if "weblog" in [tags]` 包住，
于是它对每条 SSH 日志也执行了一次并失败 → 打标签。

**【实际是什么】**

`/usr/share/logstash/pipeline/` 目录里有一个 **`logstash.conf.bak`**（备份时留下的）。

**Logstash 把目录下的配置文件【合并】成同一个管道 ——「合并」不是「覆盖」。**
于是：

| 跑的东西 | 结果 |
|---|---|
| `.bak` 里的**旧**信封 grok（带多余的 `}`）| 对每条日志**必然失败** → 打 `_grokparsefailure` |
| `.conf` 里的**新**信封 grok | 成功 → 字段全部正确 |

两套逻辑各干各的 → 矛盾现象成立。

**【怎么找到的】** ★

```
① 排除"分支条件"假设
   → docker compose exec logstash grep -n 'in \[ssh_message\]' .../logstash.conf
   → 结构是对的，tag 不可能来自它

② 排除"我的查询有问题"
   → 原来的 {"match": {"tags": "_grokparsefailure"}} 会经过分词器，不可靠
   → 改用 terms 聚合 {"terms": {"field": "tags.keyword"}} —— 精确值统计
   → 确认标签是真的（446/446）

③ 交叉验证「文件 vs ES」
   → grep -c 'Accepted' auth.log   = 8      ES 里 login_success = 12
   → grep -c 'pam_unix' auth.log   = 16     ES 里 pam_unix      = 25
   → 一个只含 8 行 Accepted 的文件，不可能产出 12 条 login_success
   → 结论：有一个【不在配置里】的 grok 在跑

④ 顺着"运行中的到底是什么"这条线
   → docker compose exec logstash ls -la /usr/share/logstash/pipeline/
   → 发现 logstash.conf.bak
```

**【正确的做法】**

```bash
# 备份永远放到不被扫描的目录
mkdir -p ~/elk/backup
cp logstash/pipeline/logstash.conf ~/elk/backup/

# 每次改完配置，先确认"运行中的是什么"
docker compose exec logstash ls -la /usr/share/logstash/pipeline/
docker compose exec logstash grep -n 'ssh_event' /usr/share/logstash/pipeline/logstash.conf
```

**【一句话教训】**

> **不要问「我写的是什么」，要问「运行中的到底是什么」。**

## 坑 7：删了文件重建，Logstash 还是读不到

**【现象】**

执行 `删索引 → 重新生成 auth.log → 重启 Logstash` 之后：

```
总数 448（期望 446）
.27 的分布和上一次几乎一样（login_failed 145 → 146）   ← 旧数据没被替换
.29 冒出 2 条 other（打标）                            ← 只读到了半行
```

**【我原来怎么想】**

`rm -f` 再重建 = 新文件 = Logstash 一定会从头重读。

**【实际是什么】**

Logstash 的 `file` input 用 **inode + 读取位置** 记在 sincedb 里。

```
sincedb:  inode=1234567  pos=54892     ← 我读到第 54892 字节了

脚本 rm -f 后重建 → 文件系统【复用了同一个 inode 号】
        ↓
Logstash：这个 inode 我读过 → 从 pos 继续读
        ↓
只读到文件尾部新增的那几个字节
```

**【怎么找到的】** ★

两个现象一起指向同一个结论：
- **旧数据的分布几乎没变** → 文件没有被完整重读
- **只有 2 条新文档，而且是 `other`（半行）** → 从中间某个字节切进去读的

**【正确的做法】**

```ruby
file {
  path => "/logs/auth/*.log"
  start_position => "beginning"
  sincedb_path => "/dev/null"        # ★ 不记进度 → 每次重启全量重读
  tags => ["ssh"]
}
```

之后工作流固定为（顺序不能反）：

```
① DELETE 索引
② docker compose restart logstash
```

**【一句话教训】**

> **「我重建了文件」≠「它会重新读」。**
> **判断依据是 inode，而 inode 你控制不了 —— 那就别依赖它。**

## ⚠️ 本篇「坑 7」与手册「坑 7」的口径冲突（必须知道）

| | 说法 | 触发条件 | 现象 |
|---|---|---|---|
| 本篇 坑 7 | `rm -f` 换 inode **不可靠**，sincedb **不重读** | 文件系统**复用**了同一个 inode | 只读到文件尾部几个字节 → 448 ≠ 446 |
| 手册 坑 7 | inode 变了被当**新文件**，**整份重读** | `sed` 重写文件 → 产生**新** inode | 2017 年索引一夜翻倍 |

**两个都对，而且都是同一个根因的两面：`sincedb` 记的是 inode，而 inode 你控制不了。**
所以解药也只有一个：做实验时 `sincedb_path => "/dev/null"`，或干脆**永远用新文件名**（手册 坑 20）。

> 📌 **教训的教训**：同一个坑在两个文件里被写成**相反的现象**，三个月后我会以为其中一条是错的。
> **一个事实只写在一个地方，别处只做索引。**
